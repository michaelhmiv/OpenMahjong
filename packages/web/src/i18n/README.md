## How to add a string

1. Write the English string in the component / lesson data as normal.
   Do not invent a key by hand.
2. Run `node scripts/extract-i18n.mjs` from the repo root. It regenerates
   `locales/en.json` with a stable namespaced key id (`play.*`, `learn.*`,
   `calc.*`, `review.*`, `common.*`), the English value, a sha256 hash of
   that value, and the source file + line.
3. Commit the regenerated `en.json` with your change. CI fails if it is
   stale (`scripts/extract-i18n.mjs --check`).

Keys are positional for lesson steps (`learn.riichi.tu3.step02.text`):
inserting a step renumbers later steps; the extractor regenerates the
keys and only strings whose text changed get new hashes.

To wire a string through the loader, call `t("namespace.key")` (or
`t("namespace.key", arg0, arg1)` for `{0}`/`{1}` placeholders). Only the
four tab labels are wired in Phase 1; the rest of the inventory is
extracted and waiting for Phase 2's component wiring.

A string that only exists behind a translate call — new UI copy with
no literal anywhere else in the code — cannot use plain `t()`: the
extractor only inventories string literals it finds, so the key would
never land in en.json. Use `tx("namespace.key", "English source",
...)` instead: the extractor records the second argument as the key's
English source under the explicit key. `tForLocale("namespace.key",
locale, "English source", ...)` is the same form for a lookup in a
named locale (the first-visit sheet's detected-language strings).
Both fall back to the English source when the key has no en.json
entry at all (extractor drift — the missing-key gate fails CI first).

## How stale marking works

Every key carries the sha256 hash of its English source string, and every
translation entry carries the hash of the English string it was translated
from (translation memory keyed by source hash). When English changes:

- The English hash changes; any translation entry whose stored hash no
  longer matches is **stale**.
- A stale key falls back to English in the app (`t()` only ever shows
  `approved` entries whose hash matches) and counts as unapproved in the
  dashboard until it is re-translated and re-approved.
- Unchanged strings are never re-translated, re-reviewed, or re-billed.

Per-key status, readable by the dashboard: `approved` (translated,
approved, hash matches — the only status ever shown), `draft`
(translated, not yet native-speaker approved), `stale` (hash mismatch or
explicitly marked), `missing` (no entry in that locale).

## Dashboard and release gate

`node scripts/i18n-coverage.mjs` reads the key files and prints a
per-language table: % approved on new/changed strings, plus glossary
coverage. `--json <path>` writes the same report as a JSON artifact.
`--gate` exits non-zero if any **shipped** locale is <100% approved.

Phase 1: there is no baseline file yet, so every key in `en.json` counts
as new/changed. English reports 100%; the four untranslated locales
report 0% and are listed as unshipped — they are never gated. CI runs
both `extract-i18n.mjs --check` and `i18n-coverage.mjs --gate` in the
build job.

## Routing + detection (Phase 2 Track A, semantics revised Track B)

- One URL per locale: English at the root, `/ja/`, `/zh-Hant/`, etc.
  for the rest (`localeFromPath` / `pathForLocale` in `index.ts`).
  `packages/web/server.mjs` serves the app shell for a locale prefix
  only when that locale is shipped; unshipped locales stay 404, so a
  crawler is never served English content at `/ja/`.
- Activation precedence: URL path locale > remembered choice
  (`localStorage`, key `openmahjong.locale.v1`) > English. Browser
  detection deliberately does NOT activate a locale: the approved
  switcher design shows a confirmation sheet for a detected locale
  instead of silently switching, so a first visit stays English until
  the user picks. `detectLocale()` / `firstVisitDetectedLocale()`
  expose detection to the sheet. A path locale for an unshipped
  locale still resolves to English.
- `applyLocaleDocumentTags(locale)` (called from `main.ts`) sets
  `<html lang>`, the canonical URL, and hreflang alternates for shipped
  locales only. With only English shipped this is lang="en" and the
  root canonical — English behaviour is unchanged.
- Per-language static pages (e.g. `/ja/learn/`) are a ship-step item:
  until they exist, a shipped locale's unmatched paths serve the app
  shell, never another language's static page.

## Machine drafts never ship without native-speaker approval

Only `approved` strings ship in a locale. Approval is by a native
speaker reading the string in context, not by another model. Machine
drafts sit in the review queue as `draft` and fall back to English in
the app. A translation that renders a locked glossary term differently
is a CI failure, not a style preference.

Owner ruling Nov 19, 2026 (SHIP NOW, community reviews later)
supersedes the hold for the core 4 only: zh-Hans, zh-Hant, ja, and
ko ship as machine translations once draft PR #90 merges, marked in
the switcher as machine translated (see above) — never passed off as
reviewed copy. The native-approval rule still governs Wave 2 and any
later locale, and community review follows for the core 4. How a
shipped machine-translated locale's draft entries display is a
#90-landing decision (status flip vs. a display-mode change) — the
loader still falls back to English for `draft` entries, so #90 must
resolve it before the locales render in anything but English; the
switcher itself is ready either way.

## Machine drafts (Phase 2 Track A)

- `locales/zh-Hans.json`, `zh-Hant.json`, `ja.json`, `ko.json` now hold
  machine drafts for all 3,716 keys: every entry is `status: "draft"`
  with the English source hash recorded. Drafts are data, not live —
  the loader only ever shows `approved` entries, and the draft files
  are not registered with it, so the app still renders English exactly
  as before.
- Models (benchmarked first on a fixed 40-string sample — see
  `scripts/i18n-benchmark.md`): Qwen `qwen/qwen-plus` for both Chinese
  locales, Gemini `google/gemini-2.5-flash` for Japanese and Korean.
  Gemini Flash-Lite failed the benchmark on meaning fidelity in both
  languages (a dots tile rendered as a characters tile) and was rejected.
  Total benchmark spend $0.0235; bulk spend per language is logged in
  `scripts/i18n-cost-log-<locale>.json` and summarised in
  `scripts/i18n-cost-log.md`.
- Driver: `node scripts/i18n-translate.mjs translate --model <slug>
  --locale <locale>` (key via `OPENROUTER_API_KEY`; the ruled source is
  Pi's credential store — see the script header. The custom.openrouter
  connector's key is broken and is never used). Translation memory:
  keys already drafted from the same English hash are never re-billed.
- Review queue: `~/workspace/mahjong-prep/i18n-review-queue/` — per
  language, every draft grouped by namespace with the English source
  alongside, plus draft glossary forms and a status file. No native
  reviewers sourced yet; nothing is approved.
- Draft glossary forms live in `scripts/i18n-translate.mjs`
  (`DRAFT_GLOSSARY`) and in the review queue. The locked glossary
  (`glossary.json`) stays `null` for every non-English locale until a
  native speaker decides each form — a draft that renders a locked term
  differently is a defect to fix in the draft pass, not something to ship.

## Known gaps / ambiguities (flagged, not silently dropped)

- Thrown error messages outside the calculator / in-person `safe()`
  paths are **not** inventoried: they are internal consistency
  assertions (replay/runner/review/tutorial/education validators), not
  UI copy. The one user-visible failure string,
  "Compatible variant content is unavailable"
  (`variant-education-ui.ts`), is listed here instead of being reworded.
- `packages/coach/src/advice.ts` `tileName` (tile names used in review
  text) is outside `packages/web/src` scope — not extracted.
- `index.html` meta description says "against the CPU", not "Bot" —
  flagged as a question for Phase 2, not reworded (extraction only).
- Dynamic/computed strings that cannot be statically inventoried
  (`tileLabel(tile)`, `WIND_NAMES[...]` interpolations) are inventoried
  as composite template keys plus fragment keys; Phase 2 rewiring must
  use the fragment keys.
- Wind/dragon display names come from the glossary, not separate UI keys.
- English lesson prose uses "pung" (61 strings) alongside the locked
  "Pon". Phase 2 must rule whether "pung" occurrences are the same term
  before translators render them.
- Lesson step keys are positional; inserting a step renumbers later
  steps (the extractor regenerates them).
- `PRACTICE_CARD_LABEL` in `american-card.ts` duplicates the Practice
  Card JSON label — the JSON is canonical, the TS const is skipped.
