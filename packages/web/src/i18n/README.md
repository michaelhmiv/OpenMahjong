## How to add a string

1. Write the English string in the component / lesson data as normal.
   Do not invent a key by hand.
2. Run `node scripts/extract-i18n.mjs` from the repo root. It regenerates
   `locales/en.json` with a stable namespaced key id (`play.*`, `learn.*`,
   `calc.*`, `review.*`, `common.*`), the English value, a sha256 hash of
   that value, and the source file + line.
3. Commit the regenerated `en.json` with your change. CI fails if it is
   stale (`scripts/extract-i18n.mjs --check`).

Keys are positional for lesson steps (`learn.riichi.tu3.step02.text`):
inserting a step renumbers later steps; the extractor regenerates the
keys and only strings whose text changed get new hashes.

To wire a string through the loader, call `t("namespace.key")` (or
`t("namespace.key", arg0, arg1)` for `{0}`/`{1}` placeholders). Phase 1
wired only the four tab labels; the rewire wired every render file
(see "Wiring" below) — a string that is extracted but never wired
renders English on a non-English locale, which is the exact bug the
rewire fixed.

A string that only exists behind a translate call — new UI copy with
no literal anywhere else in the code — cannot use plain `t()`: the
extractor only inventories string literals it finds, so the key would
never land in en.json. Use `tx("namespace.key", "English source",
...)` instead: the extractor records the second argument as the key's
English source under the explicit key. `tForLocale("namespace.key",
locale, "English source", ...)` is the same form for a lookup in a
named locale (the first-visit sheet's detected-language strings).
Both fall back to the English source when the key has no en.json
entry at all (extractor drift — the missing-key gate fails CI first).

## Wiring (the rewire: every screen body through t())

The ship translated the shell but not the bodies because extraction
and wiring are separate steps: the extractor inventories strings, the
components must resolve them. Three CI gates now enforce the whole
loop, in order, in the build job:

1. `node scripts/extract-i18n.mjs --check` — en.json is exactly what
   the extractor produces from current sources.
2. `node scripts/check-i18n-wiring.mjs` — no user-facing literal in a
   render file is rendered without t()/tx()/tForLocale(). Proven to
   fail on pre-rewire main (1,437 unwired literals + 8 ambiguous) and
   pass on the rewired tree. A new literal mints a key at step 1, so
   this step fails until it is wired.
3. `node scripts/i18n-coverage.mjs --gate` — shipped locales are 100%
   community-reviewed on new/changed strings (re-baselined at the
   rewire release; see below).

Render files (the 20 scanned by the wiring check) resolve strings in
two ways. Direct literals go through `tx("key", "English source")` —
the extractor records the fallback as the key's English source. Data
files are never touched: lesson data, curriculum, the MCR guide, and
the practice card are the extractor's source of truth, and the
renderers derive their keys positionally at render time — a variant
lesson step is `learn.<variant>.<topic>.step<N>.text`, a question
field `learn.<variant>.<topic>.q-<qid>.prompt|choice<N>|explanation|
hint`, a lesson title `learn.<variant>.<topic>.title`, an MCR pattern
field `learn.mcr.guide.pattern.<slug>.name|family|recognition|
exclusions`. `packages/web/test/i18n-derived-keys.test.ts` proves every
derived key exists in en.json with the matching English value — `t()`
returns the key id itself on a miss, so a drifted derivation would
show a raw key id on screen. Hong Kong's question builders pass the
full id (`hk-inventory`); the other tracks' helpers prefix the bare
id at runtime, so the derivation strips the prefix except for
hong-kong. Module-scope records (YAKU, NAMES, TERMS, LABELS, KEY_ROWS)
cannot call t() at import time (before initI18n), so they store
`{key, label}` and the render site resolves the key with t(); a record
that carries its own key (`{label, key}` / `{title, key}`) claims its
text under that key in the extractor.

Two resolution shapes the wiring check cannot see, both proven by the
derived-keys test instead: (1) DATA VALUES rendered raw — the check
scans literals, so a data field rendered directly (`exercise.prompt`,
`VARIANT_RELEASES[].name`, a module def title) passes it while staying
English on screen; render verification caught four such families after
the rewire (release names, the lesson-runner kicker, the practice-card
label, practice prompt/explanation/hint). Where a value's key is
slug-derived and slugs collide (the extractor suffixes "-2"), resolve
BY VALUE within the namespace, as practice-ui.ts does — never by slug.
(2) English morphology passed as an interpolation arg: templates that
carry the plural as an arg (`"{0} recorded game{1}"`) must pass
`pluralS(count)` from i18n/index.ts, never a raw `"s"` — ja/ko/zh do
not mark plurals, so a raw "s" leaks Latin letters onto their screens.

Two more shapes the extractor AND the check both miss (render
verification of every screen is the only guard): (3) literals behind
LOCAL inline helpers the extractor does not know — the Rules screen's
intro and bullets were passed to a block-local `p`/`li` helper, and
their values were already claimed by the `pages.riichi.*` inventory,
so no `ui.app` key existed; and (4) display text passed as a plain
method argument — `textScreen()` received its title (`Rules`,
`About`, …) as a raw literal and rendered it as the screen heading.
Both are fixed now (Rules body +16 keys, titles +4 keys). Derived-key
render sites that can meet unminted content degrade to the data text
via a `keyStatus(key) === "missing"` guard (`dt()` in
variant-education-ui.ts) — a key id must never reach the screen.

Extractor fixes from the rewire (see `scripts/extract-i18n.mjs`):
the mcr-guide rule runs before the generic bare-list rule (its tuple
elements were claimed under slug keys instead of positional pattern
keys); a question choice is display text by construction, so
single-digit choices ("8", "9") are forced past the length-1
code-data skip; an explicit `tx` key claims its dedupe slot; nested
tx() composition reads the outer template's spans after inner edits,
so an inner fragment stays its own key; `interpolate()` renders a
supplied argument exactly as a template literal would.

Known gaps (flagged, not fixed here): wind/dragon display names come
from the glossary, still `null` for non-English locales; the static
content pages (`pages.*`, ~250 keys) are pre-rendered HTML — per-language
static pages are a separate ship-step item; practice-ui exercise-picker
labels derived from `entry.id.replace(/-/g, " ")` have no key.
Hong Kong / Taiwanese win-breakdown pattern names (variant table,
paused state) render the English engine names: they have no standalone
keys yet — minting them is a follow-up (MCR patterns already resolve
through `learn.mcr.guide.pattern.<slug>.name`).

## How stale marking works

Every key carries the sha256 hash of its English source string, and every
translation entry carries the hash of the English string it was translated
from (translation memory keyed by source hash). When English changes:

- The English hash changes; any translation entry whose stored hash no
  longer matches is **stale**.
- A stale key falls back to English in the app (`t()` shows only
  displayable entries whose hash matches — see the display rule
  below) and counts as unapproved in the dashboard until it is
  re-translated and re-approved.
- Unchanged strings are never re-translated, re-reviewed, or re-billed.

Per-key status, readable by the dashboard: `approved` (translated,
approved, hash matches — always shown), `reviewed` (one community
reviewer who did not write the wording has read it in context and
confirms it — counts toward community-review coverage and the release
gate; shown where a draft is shown, in a machine-translated ship
locale), `draft` (translated, not yet native-speaker approved — shown
only in a machine-translated ship locale), `stale` (hash mismatch or
explicitly marked), `missing` (no entry in that locale).

## Dashboard and release gate

`node scripts/i18n-coverage.mjs` reads the key files and prints a
per-language table: % approved and % community-reviewed
(`reviewed` + `approved`, hash-current) on new/changed strings, plus
glossary coverage. `--json <path>` writes the same report as a JSON
artifact. `--gate` exits non-zero if any **shipped** locale is <100%
community-reviewed on new/changed strings (design §7.1, DECIDED
Nov 19, 2026 — see `scripts/i18n-coverage.mjs`).

Baseline: `baseline.json` snapshots every shipped key hash-current at
ship time, so "new/changed" means "changed after the snapshot". The
initial baseline is the one-time waiver for the machine-translation
ship (all ship-time keys are grandfathered); any key added or
re-sourced afterwards counts as new/changed and must earn a community
review (`reviewed` or `approved`) before a later release can pass the
gate. Regenerate it with
`node scripts/i18n-coverage.mjs --write-baseline` — only at a release
that is meant to re-baseline. CI runs both
`extract-i18n.mjs --check` and `i18n-coverage.mjs --gate` in the
build job.

## Routing + detection (Phase 2 Track A, semantics revised Track B)

- One URL per locale: English at the root, `/ja/`, `/zh-Hant/`, etc.
  for the rest (`localeFromPath` / `pathForLocale` in `index.ts`).
  `packages/web/server.mjs` serves the app shell for a locale prefix
  only when that locale is shipped; unshipped locales stay 404, so a
  crawler is never served English content at `/ja/`.
- Activation precedence: URL path locale > remembered choice
  (`localStorage`, key `openmahjong.locale.v1`) > English. Browser
  detection deliberately does NOT activate a locale: the approved
  switcher design shows a confirmation sheet for a detected locale
  instead of silently switching, so a first visit stays English until
  the user picks. `detectLocale()` / `firstVisitDetectedLocale()`
  expose detection to the sheet. A path locale for an unshipped
  locale still resolves to English.
- `applyLocaleDocumentTags(locale)` (called from `main.ts`) sets
  `<html lang>`, the canonical URL, and hreflang alternates for shipped
  locales only.
- Per-language static pages (e.g. `/ja/learn/`) are a ship-step item:
  until they exist, a shipped locale's unmatched paths serve the app
  shell, never another language's static page.

## Machine drafts — shipped for the core 4, approved-only everywhere else

Owner ruling Nov 19, 2026 (SHIP NOW, community reviews later)
supersedes the approved-only hold for the core 4 only: zh-Hans,
zh-Hant, ja, and ko ship as machine translations (PR #90), marked in
the switcher as machine translated — never passed off as reviewed
copy. The native-approval rule still governs Wave 2 and any later
locale, and community review follows for the core 4 (see
`~/workspace/mahjong-prep/community-review-design.md`).

Display rule (the mechanism, `isDisplayable()` in `index.ts`): an
`approved` string is always shown. A `draft` string is shown only in
a locale listed in `MACHINE_TRANSLATED_LOCALES` — the waiver locales
— where the language-level marking keeps it honest. No status was
flipped to `approved` or `reviewed` for the ship: every core-4 entry
is still `status: "draft"`, and the switcher marking is what makes
the ship honest. A draft in any other locale falls back to English,
as does a `stale` or `missing` key everywhere. When community review
completes for a locale, remove it from `MACHINE_TRANSLATED_LOCALES`:
its drafts and reviewed strings stop displaying and only `approved`
strings show. A translation that renders a locked glossary term differently
is a CI failure, not a style preference.

## Community review (Nov 19, 2026 ruling: ship now, community reviews later)

Hired native-speaker review is cancelled as a blocker. The machine drafts
ship marked machine-translated / community-review pending (release gate
waived for that initial ship only, by Michael's ruling), and the community
reviews them in place. Contributor guide: `docs/translating.md` (linked
from the in-app "Improve this translation" link in the More tab footer).

Per-string status, per language: `draft` (translated, not yet read in
context by an independent reviewer) → `reviewed` (one community reviewer
who did not write the wording has read the string in context and confirms
it) → `approved` (native-speaker bar: read in context and final; lessons
need native-reader transfer checks). Display follows `isDisplayable()`:
`approved` always shows; `draft` and `reviewed` show in a
machine-translated ship locale; `stale` and `missing` fall back to
English. A correction PR changes `value` only and leaves
`status: "draft"`; a separate review PR flips the status. A correction
must NOT be self-approved — enforced by
`scripts/i18n-approval-gate.mjs` (R1/R2/R3) in CI. Release gate (design
§7.1, DECIDED Nov 19, 2026): community-reviewed (`reviewed` +
`approved`) on new/changed strings, not approved-only. Full status model,
flow, and guardrails:
`~/workspace/mahjong-prep/community-review-design.md`.

Release-gate waiver for the initial ship only: `baseline.json`
(same directory) snapshots every shipped key hash-current at ship
time, so the gate (`scripts/i18n-coverage.mjs --gate`) measures
only keys that change AFTER the snapshot. Regenerate it with
`node scripts/i18n-coverage.mjs --write-baseline` at a release that
is meant to re-baseline — never silently, and never to hide a
regression: the snapshot is the waiver, and any key added or
re-sourced afterwards must earn approval (community-reviewed, per
the community-review design) before it can ship in a later release.
