# Practice and decision review — rendering proposal

**Status: proposed; not approved and not implemented as application screens.**
These files are a reviewable next-step design package for the master brief's
Learn → Play → Analyze → Practice loop. They do not change production navigation,
record progress, or represent a released Practice or decision Review interface.

## Renderings

| Screen | 390 × 844 | 360 × 800 |
| --- | --- | --- |
| Practice: wait reading with corrective explanation | [Practice rendering](practice-390.png) | [Practice rendering](practice-360.png) |
| Review: compare an actual legal discard with an alternative | [Review rendering](review-390.png) | [Review rendering](review-360.png) |

The [HTML prototype](index.html) uses the existing local fonts and tile sprite.
From the repository root, run `python3 -m http.server 4176 --bind 127.0.0.1`, then
open `/docs/design/proposals/index.html?view=practice` or `?view=review` on that
local server. No third-party requests, account, or production service is needed.
Buttons demonstrate appearance only; exercise counters and selected states are
authored mock states. The prototype never saves progress. The two navigation
links switch between the proposed surfaces.

## What is being proposed

- A Practice surface reachable by guests and account users. Its first exercises
  use the validated curated corpus, give feedback without advancing wrong
  answers, and keep the reasoning visible. The screenshot shows a completed
  wait-reading answer; interactive validation must use the existing practice
  core in the implementation PR.
- A decision Review surface that defaults to player perspective, shows the
  original hand, compares exact shanten and unseen-copy counts, and qualifies
  the strategic ranking. The screenshot does not imply an optimal discard,
  win probability, numerical mistake grade, or analysis of hidden hands.
- A direct practice action from review. For this example, **Practice tile
  efficiency** would open a relevant authored exercise. A game-derived graded
  exercise must first pass a separate semantic validation gate; it is not
  supplied by this prototype or the current curated exercise schema.
- Compact previous/next decision controls. Both are disabled in this single
  position example; a full implementation enables them according to the
  headless review navigator's bounds.
- A proposed learning navigation row with Practice and Review. Its placement
  in the actual application, guest discoverability from Learn/History/results,
  and relationship to existing navigation require a design decision. This
  prototype does not silently amend the approved screen inventory.

No lesson completion permanently locks content. Local-only progress and account
synchronization need an explicit product/data contract before this UI claims
cross-device persistence.

## Evidence behind the content

**Practice** uses `wait-ryanmen` from
[`packages/web/src/education/practice.ts`](../../../packages/web/src/education/practice.ts).
The hand is `123m123p777z55s45m`. Its shape-completing tile types are exactly
`3m` and `6m`. The explanation deliberately distinguishes shape completion from
a legal win, which also needs a yaku and must satisfy furiten rules.

**Review** uses the public first-draw view for seat 0 from seed
`design-review-2`, generated by the current built engine 2 and policy 2 under
`openmahjong-riichi@1`. The example player choice is the legal discard `3s`;
it is authored for the mockup, not presented as a recorded user's mistake.
The [captured public facts](review-facts.json) contain only PlayerView, legal
TurnContext, and the relevant evaluator results. No future outcome was
inspected:

| Candidate discard | Shanten after | Unseen improving copies |
| --- | ---: | ---: |
| 3s | 3 | 42 |
| West | 3 | 58 |

The difference is 16 unseen improving copies. Those copies may be in other
hands or the dead wall. They are not guaranteed live-wall draws. Preference
for a candidate is a heuristic; the arithmetic and current visible counts are
exact properties of the supplied view. The independent QC report recomputes
these values from that view.

## Approval required before application implementation

The existing [design authority](../../design-rules.md) says in §6:

> A new screen requires a brief amendment and an approved rendering.

And in §10:

> No UI change is built before its rendering is QC-passed and approved by Michael.

Approval is needed for the **Practice addition to the screen inventory**, the
**Review composition and navigation placement**, and the **Practice/Review
learning navigation**. These renderings and their proposed dimensions are the
concrete material to review. An implementation PR must amend the design rules
with the approved screen/navigation decisions in the same change.

Independent QC passed both proposals at 390 × 844 and 360 × 800: all controls
were at least 44 × 44px, UI text at least 11px, no overflow or axe violations,
and minimum measured text contrast 6.58:1 for Practice and 4.89:1 for Review.
Fonts and the displayed engine facts were independently checked. The
[QC report](qc-report.json) and [QC notes](qc-notes.md) record the measurements
and are separate from owner approval. It is not a claim that Michael approved the
design, nor a complete WCAG audit. Keyboard behavior, focus management, screen
reader announcements, real feedback/error states, loading, offline persistence,
full-table decision replay, large text, tablet/desktop adaptation, and
cross-device sync still require implementation and verification.

## Proposed implementation acceptance criteria

1. Reuse the existing practice validator and versioned review core. Every
   displayed value comes from structured evidence under the recorded ruleset.
2. Wrong answers explain the issue and remain retryable. Assisted and
   independent attempts remain distinct in skill evidence.
3. Make tiles, navigation, disclosure, and next/previous controls keyboard
   usable with names, visible focus, and meaningful disabled states.
4. Preserve the 44px control floor at 360px width, 11px text floor, approved
   tokens/fonts, reduced motion, and guest access. Keep navigation visible and
   allow content to scroll when text grows.
5. Resume exercises reliably; label local-only storage honestly. Do not claim
   account synchronization until conflict and offline behavior is implemented.
6. Never feed hidden/future information to player-perspective analysis. Keep
   legacy v1 review display-only until a compatible analysis adapter exists.
7. Test the full lesson → guided game → decision review → relevant practice
   → return-to-play path, and capture actual application evidence before
   calling that learning loop complete.
