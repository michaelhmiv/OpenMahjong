# Multiplayer implementation brief

**Delivery target.** A player opens Open Mahjong, picks a ruleset, finds three opponents or gathers friends, plays unaided, and can finish even if someone leaves. The results page offers personal analysis, reveal of all four hands after the match, and another game. The same journey must work for Riichi, Hong Kong Old Style, MCR WMO 2006, and Taiwanese Every-flower. Riichi offers East and East–South. The three variant engines accept East, South and Full length values. Show the actual round count and profile in the room and queue. American study and scoring tools do not supply a fifth match engine. [Rules and profiles](variants.md)

**Status.** Implemented on PR #87. [Runtime configuration, tests and rating calibration](multiplayer-operations.md) documents the shipped interfaces and rollout gates. The original brief was scoped against main at `4baf5ea`. The product scope below incorporates the owner's decisions. Transport, clock defaults, rank eligibility and abandonment settlement are engineering or policy proposals. A fixture, endpoint or bot simulation alone does not deliver a playable milestone.

## From arrival to the result

| Entry | Who can sit | How a table fills | Result |
| --- | --- | --- | --- |
| Open Play · Friendly | Guest or account with a display name | Match compatible players. A player may opt into filling custom rooms and see the settings and bot count before accepting. | Unrated standings |
| Open Play · Ranked | Proposed launch policy requires four distinct accounts and human seats at start | Service assigns opponents and seats by profile, length and rating. Widen the skill range with wait time. Keep rules, clocks and length fixed. | Official placements, rating changes, ranked requeue |
| Custom room | Guest or account with a display name | Host can combine invited friends, explicitly added bots and opt-in Friendly players. Show which seats are available, reserved, ready or occupied by bots. | Always unrated |

A guest opening an invite chooses a name and joins in that browser. Offer the existing Google account flow and an editable public display name. Preserve the invited room through sign-in using a validated local return target. Make names display-only, length-bounded and safely rendered as text. Bind membership to an opaque guest session or account ID. Allow guest-to-account conversion in one transaction only from the controlling session. Define guest review access for the life of that session and show that limit in the results UI.

Use an explicit web entry such as `/#/join/<invite>` and `/#/match/<id>`. The existing static server serves the root and returns 404 for unknown file paths. Remove the invite from the address after redemption. Room links grant entry to available seats. Only an existing membership can reclaim a seat or access a finished game. Expire/revoke invites at start. Transfer host controls to the next seated human if the host leaves before play. Once started, the match progresses independently of its creator. [Web entry](../../packages/web/server.mjs) · [Current API and sessions](../../packages/server/src/app.ts)

During play, show the local hand, public board, current decision, time remaining at live tables, connection state and any bot-controlled seat. Legal buttons and tile labels stay available. Suppress strategic hints, recommended discard styling and calls to the coach for all human seats. After settlement, show placement, scores, transfers and any rating change. **Analyze** opens that player's perspective. **Reveal all hands** is an explicit personal toggle in the finished match. **Rematch** collects consent for a fresh Friendly table and fresh walls. **Play Ranked Again** enters matchmaking. A user can review independently of the other three.

### Correspondence (unlimited)

Offer **Live** and **Correspondence · No time limit** for all four playable variants. Show the pace before a player joins a queue, accepts a room offer or agrees to a rematch. Match only players who chose the same pace. Friendly and custom correspondence support invited guests, accounts and deliberately added bots. Ranked correspondence uses its own four-account pool and rating history under the ranked release gate. Custom rooms remain unrated.

A player can discard today, close the app, and return days later. Store `pace` on the room, ticket, match and replay. For correspondence store `deadlineAt: null` for turns and claims. Absence, session expiry, worker restarts and elapsed time never trigger a pass, discard, loss or bot substitution. Seats assigned to bots at setup still answer normally. Pace is fixed at match start. Permit an explicit leave or a consensual end through a separate command with published settlement rules. Until players act or explicitly end the game, it may remain pending indefinitely.

After a discard, privately prompt only seats with a legal response. Advance immediately when nobody can claim. Otherwise wait for the replies needed to determine the result under the variant's priority and passed-win rules. A submitted chi can remain pending for days while another seat considers ron. Give other players the neutral status **Waiting for table**. Never identify a possible caller or count outstanding offers on another player's screen.

Add **My games** with **Your move** and **Waiting for table** filters. An authenticated list endpoint returns each member's tables and whether they have an unanswered decision. Players can have several correspondence games alongside a live game. Persist membership independently of transport and reload the current seat snapshot on return. Signed-in players can resume on another device. Give guests a private, revocable seat recovery code at join so a browser cookie's lifetime does not become a hidden turn limit. Keep that credential separate from the room invite.

### Walls and live information

The existing deterministic shuffle reduces each hand seed to a 32-bit state. Riichi and the variant coordinator include a seed in internal events. The live API should use Fisher–Yates over the profile's canonical inventory with Node's cryptographically uniform `crypto.randomInt(0, i + 1)`. Generate each hand once on the server. Persist the private permutation and serial atomically before the deal becomes visible. Replay/recovery reads precisely that permutation, including red fives, flower tiles and replacement draws. A fresh hand gets independent randomness even after a repeat or restart. [Solo RNG](../../packages/engine/src/rng.ts) · [Riichi wall layout](../../packages/engine/src/wall.ts)

Variants already accept a wall factory. Riichi's finite wall queue falls back to seeded generation when exhausted. Give authoritative play a mandatory hand-indexed wall provider. A missing committed wall during recovery is a recovery error. Keep solo seeds and historical engines executable. Serialize the live payload from an allowlist rooted at the engine's seat view, with public board changes, seat-local prompts and visible deadlines. Never serialize raw engine events, ORM rows, recovery snapshots or review logs on a live channel. Exclude live messages and replay bodies from diagnostics, analytics and service-worker caches.

## API and ordering contract

Start on the existing Node API with authenticated HTTP commands and a credentialed Server-Sent Events stream per active browser. Mahjong needs ordered server updates and small player intents. This design reuses the request, cookie, origin, CSRF and error paths already exercised by this repo. A socket transport can implement the same messages if Railway streaming measurements warrant it. Lichess separates challenge acceptance, server-side move validation, live round recovery and finishing into distinct responsibilities. Apply that division here. [Lichess challenges](https://github.com/lichess-org/lila/blob/master/modules/challenge/src/main/ChallengeJoiner.scala) · [Move validation](https://github.com/lichess-org/lila/blob/master/modules/round/src/main/MovePlayer.scala) · [Round client](https://github.com/lichess-org/lila/blob/master/ui/round/src/socket.ts) · [Finishing](https://github.com/lichess-org/lila/blob/master/modules/round/src/main/Finisher.scala)

| Route under `/api/online` | Contract |
| --- | --- |
| `POST /guests`, `POST /profile` | Issue an expiring HttpOnly guest cookie and CSRF token, or update the authenticated player's display name. Validate the app origin on guest creation. |
| `POST /rooms`, `POST /rooms/join`, `POST /matches/:id/room` | Create, redeem invite, reserve a seat, ready, add a bot, offer free seats, leave or start. Host-only mutations check ownership. Retrying start returns the same match ID. |
| `POST /queue`, `POST /offers`, `GET /games` | The queue returns a waiting-room ID. Its seat stream carries private offers or assignments. Cancel through the room’s leave command. An offer has an expiry. Lock and recheck tickets, room seats, readiness and compatibility in the assignment transaction. A concurrent cancel or invite has one committed outcome. |
| `GET /matches/:id`, `GET /matches/:id/stream` | Authorize the membership on access and recheck at expiry or revocation. Return a snapshot for this seat and deliver projected updates. On reconnect or cursor gap, send one current snapshot, its board revision and its original deadline (null for correspondence). Bound queues for slow clients. |
| `POST /matches/:id/actions` | Require the protocol version, unique action ID, base board revision, and index into the seat’s legal choices. The controlling browser includes its ID and generation. Derive seat from the authenticated principal. ACK a durable receipt. Duplicate retries return the original receipt. A reused ID with changed contents or stale decision returns conflict and the recovery path. |
| `GET /matches/:id/review`, `POST /matches/:id/room` with `kind=rematch` | Require a participant and committed final settlement. Review returns the versioned official timeline. Rematch offers expire and create at most one new Friendly room. |

**Simultaneous calls.** Use the match ID and board revision to identify the discard window. Each eligible seat receives only its own offers. Persist one private answer per seat/window. Accept remaining seats' answers against the same base revision even after the first answer is durable. A private response must not advance the publicly visible board revision or disclose that another seat could claim. At a live table's server deadline, treat missing claims as passes and invoke the profile's resolver. Preserve Riichi head-bump ordering and ron before pon/kan before chi. Commit the resolved board change once. A deadline tick racing the last response acquires the same match lock and checks database time. Keep internal action sequence, public board revision and per-seat stream cursor distinct. Test reversed arrival orders. [Riichi discard resolver](../../packages/engine/src/game.ts) · [Variant call stages](../../packages/engine/src/variants/game.ts)

**Live clocks and disconnects.** Proposed initial playtest settings are 20 seconds for an ordinary decision and 5 seconds for an optional claim. Publish the chosen preset before seating. A missed claim passes. A timed-out turn discards the just-drawn tile if legal, otherwise the first legal discard under a documented stable ordering. Handle forced actions with a ruleset-specific legal default. Track absence on a separate 60-second deadline from the last confirmed disconnect, including browser suspension detected by a bounded heartbeat. Treat a continuously connected player who misses decisions as idle and start an idle deadline from the first missed decision. Merely waiting for someone else's turn is normal. A user action or acknowledged reconnect clears the applicable absence state. Exercise repeated reconnects and idle timeouts so they cannot indefinitely stall the table. Lichess scales its reconnect allowance by game speed and can let an opponent claim a result. Four-player tables continue under bot control after the minute. [Lichess clock policy](https://github.com/lichess-org/lila/blob/master/modules/round/src/main/RoundSocket.scala) · [Claim handling](https://github.com/lichess-org/lila/blob/master/modules/round/src/main/RoundAsyncActor.scala)

Show who the bot is covering. Restore human control at the next uncommitted decision boundary and invalidate the previous controller's decision token. Use a single controller generation per seat across tabs, reconnects and bots. Dropping an old connection must not mark a newer connection absent. Log whether each committed action came from a human, clock default or bot.

## Durable writes and recovery

Add ordered SQL migrations after the repository's existing migrations. Use UUIDs, explicit states and foreign keys. Keep the public projection out of the private recovery record. Extend the Postgres integration suite using its loopback test database. [Migration runner](../../packages/server/src/migrations.ts) · [Store integration fixtures](../../packages/server/test/postgres-integration.test.ts)

| Data | Constraint or transaction |
| --- | --- |
| Principals, rooms, seats and queue tickets | Enforce unique room/seat and room/principal, at most one active live ticket or live match assignment per principal, independently owned correspondence memberships, and seat indices 0–3. Serialize final-seat assignment and match creation. Enforce ranked eligibility again at start. |
| Matches, hand walls, decisions and receipts | Persist engine/profile/policy/protocol versions, status, board revision and deadlines. Unique wall per match/hand, receipt per match/actor/action ID, answer per window/seat. Lock the match row for commands, timeout and takeover. Persist accepted input, state transition and result before ACK or fanout. |
| Recovery | Restore from durable hand boundary plus subsequent decisions and private pending answers. Rebuild any in-memory coordinator, verify the resulting revision, schedule timers only for live matches with stored deadlines and publish a seat snapshot. Guard stale workers during rolling restarts with a database-backed owner generation in the write predicate. |
| Results, replay access and ratings | One official result per match and one placement per seat. Persist placements, controller changes and final replay reference atomically. Use a unique rating ledger entry per match/account and a versioned settlement policy. Handle concurrent rating updates in stable account order. Account deletion removes identity/access and anonymizes shared placements while preserving the other participants' history. |

**Ranked policy to settle before enabling the queue.** Start with four human accounts and compare a four-placement rating model with ties against the benchmark described in the existing proposal. Rate separately by ruleset, with match length explicit in matching and calibration. Proposed abandonment policy caps the covered player's positive rating change at zero after the first committed bot move, retains losses, and settles the other seats from the official table. Mark platform-caused interruptions separately and void affected rating writes. Measure bias and rating drift from capped gains and disconnections on simulations before adopting the policy. Verify tied placements, concurrent finishes, already-settled retries and multiple covered seats. [Rating research](multiplayer.md)

Use the existing Vitest, Playwright and Postgres patterns. Add a four-context multiplayer script beside the [browser harness](../../scripts/browser-harness.mjs), and run it against the built web/API with independent sessions and a disposable Postgres. Verify emitted workspace imports and all existing build/test gates. Record actual checks, failures and observed latency with each implementation PR.

**Correspondence acceptance across milestones 2–6.** For each variant, persist an unanswered turn and a contested discard, disconnect every browser, advance a test clock by 30 days, restart the API, then reauthenticate. Verify the original decision IDs, unchanged board revision, concealed hands and lack of timer or takeover writes. Submit the outstanding replies in reversed order and verify the same rightful claim. Include a discard with zero legal callers, a guest returning after cookie expiry, two concurrent games with different pending seats, and a completed match with results, reveal and rematch. Verify live 60-second cover still fires and live/correspondence queue tickets never pair.

## Railway rollout

Read-only inventory on November 18, 2026 showed one OpenMahjong environment, production, with one running replica each for web, api and Postgres. All three reported online. The API boots its migrations before listening, and the web service serves a built static bundle. Begin with the existing API process and Postgres. The design adds no dedicated realtime service to the initial topology. [API build and health configuration](../../railway.api.json) · [Web build and health configuration](../../railway.web.json) · [Operations notes](../deployment.md)

Use local integration and a disposable environment for route, origin/cookie and real Railway streaming tests before opening production entry. Exercise two browsers across idle intervals and a rolling API restart. Measure queue age per format, active tables/connections, decision-to-update latency, event loop delay, reconnect recovery, bot substitutions, projection size and duplicate settlement attempts. Exclude player hands, invite tokens and raw actions from logs. Set concurrency and streaming heartbeat limits from these measurements.

Ship additive schema first, then compatible API readers/writers, then client entry points. Gate new room creation, Friendly assignment and Ranked assignment independently. Before a rollback, close new admissions, allow existing tables to finish or move them to a compatible worker, and retain the engine versions needed to replay open matches. Exercise a database restore and compare official results and rating ledger entries before enabling Ranked. Record proposed clock values, ranked abandonment handling and retention periods for guest credentials, private walls and participant reviews in the release decision record.
