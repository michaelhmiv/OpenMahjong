# Learning progress and review

Implemented lesson progress remains under `openmahjong.tutorial.v1` in localStorage and the account settings blob. Completion IDs union on sign-in. If either active lesson is still incomplete in that union, prefer it; ties stay local-first. No timestamp exists for historical records, so larger step numbers are not presented as proof of recency. Progress is personal and client-authoritative, with no competitive trust implications.

`education/practice-progress.ts` provides a separate local-first schema, `openmahjong.practice.v1`. Attempt records include unique ID, exercise/content version, taxonomy version, ruleset, skill, timestamp, correctness, assisted status, response duration, and attempt number. Parsers bound storage to 2,000 attempts, reject unsupported versions/invalid fields, and deduplicate IDs. Unknown future schemas yield an empty supported record rather than an unsafe interpretation. This is currently a module API; existing App/account sync does not yet consume it. No private data is made public or transmitted by this module.

Skill evidence reports each skill's independent first attempts, correct first attempts, assisted count, retry count, last practice/success, and accuracy or `null` when there is no evidence. Accuracy is the ratio `unassisted correct first responses / unassisted first responses`. Hint-assisted responses and retries do not enter that denominator. Tutorial completion and guided-game completion are exposure records and are not automatically converted into mastery. Response speed is recorded but does not affect accuracy or schedule.

The initial review schedule is deliberately transparent: consecutive independent first-response successes use intervals 1, 3, 7, 14, then 30 days. An independent error resets the interval to one day. A retry or hinted answer does not erase the error or postpone review. Exercise versions have separate schedules. Recommendations list due items first (oldest due first), then unseen items in catalog order. All exercises remain directly accessible.

These intervals are an initial product hypothesis, not a calibrated forgetting model. The code does not claim expert proficiency, competitive skill, or causal improvement. Before a dashboard ships, add account conflict/sync handling, response-event integration, retention controls, browser refresh/offline tests, version-aware insights, and learning transfer evaluation. Browser-only storage can be lost when site data is cleared; this must remain clear in the product when practice is exposed.
