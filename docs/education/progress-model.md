# Learning progress and review

Implemented lesson progress remains under `openmahjong.tutorial.v1` in localStorage and the account settings blob. Completion IDs union on sign-in. If either active lesson is still incomplete in that union, prefer it; ties stay local-first. No timestamp exists for historical records, so larger step numbers are not presented as proof of recency. Progress is personal and client-authoritative, with no competitive trust implications.

`education/practice-progress.ts` provides a separate local-first schema, `openmahjong.practice.v1`. Attempt records include unique ID, exercise/content version, taxonomy version, ruleset, skill, timestamp, correctness, assisted status, response duration, and attempt number. Parsers bound storage to 2,000 attempts, reject unsupported versions/invalid fields, and deduplicate IDs. Unknown future schemas yield an empty supported record rather than an unsafe interpretation. The Practice view consumes this API. It persists guest attempts locally by default; the App supplies account-owned progress and handles account-scoped caching and synchronization through the progress callback. `persistLocally: false` prevents the view from reading or overwriting the global guest attempt store. The evidence module itself makes no network requests and exposes no private data publicly.

Skill evidence reports each skill's independent first attempts, correct first attempts, assisted count, retry count, last practice/success, and accuracy or `null` when there is no evidence. Accuracy is the ratio `unassisted correct first responses / unassisted first responses`. Hint-assisted responses and retries do not enter that denominator. Tutorial completion and guided-game completion are exposure records and are not automatically converted into mastery. Response speed is recorded but does not affect accuracy or schedule.

The Practice session has a separate bounded key, `openmahjong.practice-session.v1`, scoped to the same owner by the App. Reload preserves selected answers, current content version, assistance, and the number of attempts already made. It cannot turn a retry into an independent first response. A shown explanation, corrective feedback, or immediate revisit within the view marks subsequent responses assisted. Numeric response time measures the active presentation after reload; speed has no role in accuracy or scheduling.

The initial review schedule is deliberately transparent: consecutive independent first-response successes use intervals 1, 3, 7, 14, then 30 days. An independent error resets the interval to one day. A retry or hinted answer does not erase the error or postpone review. Exercise versions have separate schedules. Recommendations list due items first (oldest due first), then unseen items in catalog order. The screen uses this order for its initial exercise when no explicit or saved choice exists, and for the optional `Recommended practice` action in the evidence disclosure. A requested skill restricts initial suggestions to that skill; the selectors remain unrestricted. `Next exercise` follows the chosen category. There is not yet a full due-review dashboard.

These intervals are an initial product hypothesis, not a calibrated forgetting model. The code does not claim expert proficiency, competitive skill, or causal improvement. Before a full insights dashboard ships, verify account conflict/offline synchronization, add explicit retention controls and version-aware insights, and evaluate transfer from practice to independent gameplay. Browser-only storage can be lost when site data is cleared; the Practice evidence panel states this limitation.
